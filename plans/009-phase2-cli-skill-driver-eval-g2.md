## Why this matters

Phase 2 is "done" only when a song really goes in and a correct beat-synced video comes out,
repeatedly, and the owner can drive it in the two ways the project promises: the web editor
(Phase 3) and a command-line tool that Claude Code can use. This plan adds the CLI (a thin
client with no logic of its own), the project skill that teaches Claude Code the flow, a
throwaway browser page so the owner can see the pipeline before the real UI exists, and one
eval script that measures what G2 asks for and writes a results table plus the two review
sheets. It ends with the evidence file for the owner's G2 decision, with every number either
measured or marked, plainly, as not measured and why.

### Step 2: The commands (T-2.27)

One HTTP call per step, mapped by operation id (all paths under `/api/v1`):

- `new <song> [--title T] [--vibe "<text>"] [--keywords w1,w2,...] [--duration 15|30|60]`: `create_project` with `options` (`vibe`, `keywords_override` from splitting the comma list, `duration`; the API validates, the CLI holds no rule), then `upload_song` streaming the file (`httpx` `content=<file object iterator>`, `Content-Length` from `os.stat`, `Content-Type: application/octet-stream`, `X-Filename: <percent-encoded basename>`; never read into memory); prints the project id. On a failed upload the project id is still printed in the error details so the operator can retry (the endpoint allows re-sending). `new` does **not** wait for the analysis: the skill follows with `status <id> --watch`.
- `show <id> --json`: `get_project`, then `get_analysis` when `analysis` is non-null, then `get_plan` when `plan` is non-null; merged into `ShowOut` (pydantic, `cli/schema.py`): `schema_version "1"`; `project {id, title, ui_status, status_reason, flags, options}`; `song {duration_s, codec, sample_rate, channels}` (**no filename**); `analysis {tempo_bpm, tempo_octave_adjust, confidence {score, band, reasons}, fallback, n_beats, n_downbeats, sections [{id, start_s, end_s, label, energy}], segment, low_confidence_ranges}` where `n_beats` and `n_downbeats` are the **lengths** of `beats_s` and `downbeats_s`; `keywords {source: provenance.keyword_source, override: options.keywords_override}`; `plan {version, frozen, total_frames, n_cuts}` or null; `render {id, state, mode_a_state}` or null. **Not included** (SEC-169): `energy_curve`, `waveform_peaks`, the beat arrays themselves, any audio or file path. The energy signal Claude gets is `sections[].energy` (`e1` to `e4`), not a computed summary (no client-side statistics). Without `--json` it prints a short readable summary. The output models are exported to `packages/contracts/schemas/saveclock-<cmd>.v1.schema.json` by `scripts/export_cli_schema.py`.
- `keywords set <id> <words...> [--no-wait] [--timeout S]`: `get_plan` for `base_version` (`version`), then `patch_plan` with `{"base_version": v, "ops": [{"op": "set_keywords", "keywords": [...]}]}`; a 409 `plan_version_conflict` is retried once after re-reading the plan (`details.current_version`); a 202 returns `{job_id}`; unless `--no-wait`, poll `get_project` every `POLL_S` up to `WAIT_REPLAN_S` until `ui_status == "draft"`, then apply P9-4 (success only when `plan.version > v`; print the new version and `keyword_source`; otherwise exit 1 with `status_reason`); `ui_status == "failed"` exits 1 with `status_reason`. 409 `conflict` reasons `wrong_state`, `job_active`, `render_active` are shown as the API's code and reason, never retried.
- `plan <id>`: `get_plan` only; `--json` prints the plan, otherwise a table of cuts (index, frames, section, clip id, locked).
- `render <id> [--plan-version N] [--no-wait] [--timeout S]`: `create_render` (an identical active or ready render is returned by the API), then poll `get_render` until `ready` (print `render_id` and a one-line verify summary from `verify`) or `failed`/`canceled` (exit 1 with `error_code`); wait `WAIT_RENDER_S`. 507 `insufficient_storage` and 409 `conflict` print their codes and reasons.
- `export <id> --mode a|b [--out DIR] [--force] [--timeout S]`: the render is `project.render` from `get_project` (none, or not `ready` -> exit 1 `conflict`, nothing else is called); `a`: `request_mode_a`, poll `get_render` until `mode_a_state` is `ready` (`failed` -> exit 1; wait `WAIT_MODE_A_S`), then `download_render` `with_song`; `b`: `download_render` for `silent_video`, `cutlist_json`, `cutlist_csv`, then `get_credits` and print the credits `text`. Downloads stream to disk; the target name is the basename of the **sanitised** `Content-Disposition` filename (`filename*` preferred), never a path from the server; no overwrite without `--force`; written with mode 0600 through a temp file then rename; the output directory must exist.
- `status [<id>] [--watch] [--timeout S]`: with an id: `get_project` (`ui_status`, `status_reason`, plan and render summaries); `--watch` follows `stream_events` with the small SSE reader in `cli/sse.py` (handles `retry:`, comments, multi-line `data:`), prints `progress` and `state` events, and stops per P9-5 (exit 1 on `failed` or `ui_status` `failed`/`canceled`); a 409 `too_many_streams` falls back to polling. Without an id: `list_projects`, one line per project (id, `ui_status`, title).
- `open <id>`: no HTTP; `webbrowser.open(f"{app_origin}/projects/{id}")`, printing the URL when no browser can be opened.

## Rollback

`git revert` the branch commits (no migration, no endpoint). The CLI, skill, driver, eval and override file vanish with the revert; `Settings` regains `saveclock_api_url` and loses `dev_driver`; regenerate the env docs (`make env-docs`) in the same revert. The driver is off by default, so reverting is not urgent. Results under `eval/results/` are text files and can be deleted. `.venv` folders created by `uv run` are git-ignored.

## Maintenance notes

- The CLI is a thin client: when an endpoint changes, the CLI changes **only** if the call shape changes; `test_cli_endpoints.py` and the generated schemas fail first. A new command needs: its row in the ARCHITECTURE §2 table (a doc change by the owner), `ENDPOINTS`, the schema, the skill table row, and a test row. A new `ErrorCode` or `ConflictReason` fails `make skill-check` until the skill's table has it.
- The CLI and eval waits are derived from `config.py`; when a budget grows, the wait follows and a test fails if it does not.
- The skill's facts are guarded by `make skill-check`; wording is not. Re-run the dry run when the flow changes, and after any change to keyword rules or error codes.
- `eval/thresholds.json` is a guarded copy of QUALITY numbers; update QUALITY first (owner), then the JSON.
- Timings other than `verify.render_ms` are client-observed upper bounds (D-2). If the owner wants server-side stage timings, that is a read-only field on an existing response, a plan 006 to 008 follow-up, not a change here.
- The soak's "100 consecutive" counter resets on any non-excluded failure by design; the partial file keeps the history so a flaky run is visible, not hidden.
- `compose.fakes.yml` exists only for tests and evidence; `make dev` never reads it. If a future compose change adds a worker-like service, the override needs the same variables.
- Reviewer: scrutinise `cli/client.py` (host check before any transport, redirects, headers), `cli/files.py` (names and permissions), `scripts/saveclock` (cwd and symlinks), that `show --json` stays a summary, that the driver is absent unless the flag is set and reads the API through the direct origin, that no review sheet or decision line was filled, and that the evidence never turns a missing measurement into a pass.
